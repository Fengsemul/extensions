A practical Firefox extension cannot reach a literal theoretical minimum across CPU, GPU, RAM, network, and disk simultaneously. Some goals conflict:

    Fast exact lookups require an indexed local copy, increasing disk use.
    Atomic replacement requires temporary duplicate storage.
    Dynamic filtering requires a content script and observer.
    True request blocking requires browser-level request permissions and reliable Firefox support.
    Automatic pagination necessarily increases network, CPU, RAM, and DOM use.

The best low-resource design is therefore:

    Keep the v3 two-slot primitive-key database.
    Remove automatic pagination, CAPTCHA polling, experimental window.stop(), and inactive module code from the minimal build.
    Inject only on explicitly supported search domains.
    Use one observer only while the tab is visible.
    Scan added DOM subtrees once, in bounded batches.
    Cache final hostname decisions, not PSL objects or full rule lists.
    Delete matched result containers immediately.
    Use a dedicated browser-level blocker such as uBlock Origin for network requests.
    Do not attempt CSP injection or page networking API patches.
    Keep optional module removal in a separate edition, not the minimal filtering core.

Using document_idle avoids competing with initial page construction. It may hide results fractionally later than document_start, but generally reduces interference and startup cost.
Database

Keep the v3 two-slot database.js unchanged in the minimal folder. It is already the right production-storage design:

    primitive string keys;
    value 0;
    two fixed slots;
    no generation/type duplication per key;
    bounded imports and deletion;
    file-aware manual rules.

Do not replace 0 with null. The lookup code correctly treats undefined as absent, and 0 as present.
What this design improves

    CPU: no pagination timers, module-removal scans, settings normalization, or optional branches.
    RAM: only a bounded hostname cache, bounded message batches, and bounded DOM roots.
    GPU: blocked result nodes are deleted; animations can be disabled with static CSS.
    Network: the filter itself creates no network requests, but it does not block search-engine requests.
    Disk: two-slot primitive-key IndexedDB remains the best crash-safe Firefox-local compromise.

For truly minimized network traffic, use the minimal extension alongside uBlock Origin. A custom MV3 implementation cannot reliably outperform a mature request blocker without broad permissions, large rule machinery, and additional runtime complexity.

Extensions to avoid combining
uMatrix

uMatrix is no longer the best default choice for ordinary users. It offers powerful matrix-based control but requires maintenance and can overlap heavily with uBlock Origin.

For lower overhead and fewer conflicts:

    Use uBlock Origin alone for network filtering.
    Use its advanced mode only when necessary.
    Do not run uMatrix and multiple other request blockers together.

NoScript

NoScript can save substantial resources by blocking scripts, but modern search engines may break. It is useful only if you are prepared to build per-site permissions.
Auto Tab Discard

A tab-unloading extension can save RAM, but Firefox already has tab unloading. Try the built-in behavior first to avoid another persistent extension.
Userscript guidance

A userscript manager adds its own extension process, injection logic, update checks, and storage. For a few selectors, uBlock cosmetic filters are lighter than a userscript.

Use a userscript only when you need behavior that static filters cannot provide, such as:

    Removing a module based on complex text.
    Rewriting a destination URL.
    Waiting for a particular dynamic state.
    Adding controls.

For simple hiding, prefer:

example.com##selector

over a MutationObserver userscript.

    DuckDuckGo Lite/HTML or Wiby when practical.

    Keep Google automatic pagination disabled.
    Avoid a second network blocker unless you need manual script control.
    Close DevTools outside testing.
